3. SOFTWARE RESOURCE USAGE POLICY
--------------------------------------------------------------------------------
AuraOrbit operates on host machine resources in accordance with the following
transparent policies:

a. CPU & Process Execution Policy:
   - AuraOrbit provides local code execution and terminal emulation features.
   - When you trigger "Run Active File" or execute commands in the Terminal,
     the Software invokes local operating system compilers (e.g., javac, gcc),
     interpreters (e.g., python, node), and shell processes (bash, zsh, powershell).
   - CPU scheduling is throttled via asynchronous virtual and daemon worker
     threads. Real-time linter diagnostics run on a 500ms sliding-window debounce
     to prevent CPU thrashing.
   - Process termination hooks guarantee that closed terminal instances and
     background compiler runs are cleanly terminated without leaving zombie or
     orphaned processes.

b. Memory & Storage Policy:
   - AuraOrbit employs virtualized viewport rendering (RichTextFX). Only visible
     lines of text allocate scene-graph nodes, maintaining constant O(1) RAM
     utilization even with massive files.
   - File saves are executed atomically using temporary file staging (.tmp)
     followed by atomic replacement and safety-net backup (.bak) creation to
     prevent data loss during sudden hardware or operating system interruption.

c. Network & Peer-to-Peer Collaboration Policy:
   - AuraOrbit contains an optional local and network collaboration engine.
   - All collaborative sessions require user initiation, cryptographic token
     validation (HMAC-SHA256), and rate-limited operation processing.
   - AuraOrbit DOES NOT collect, transmit, or monetize any personal telemetry,
     source code, or keystrokes to any unauthorized central servers.

d. AI Services & API Key Storage:
   - Integrated AI features (OpenAI, Google Gemini, xAI Grok, Local Ollama)
     operate strictly on an opt-in basis.
   - API keys provided by the user are stored locally in the operating system's
     secure preferences subsystem and are transmitted exclusively over encrypted
     HTTPS connections directly to the respective API provider.
